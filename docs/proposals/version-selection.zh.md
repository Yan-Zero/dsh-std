# 协议版本选择参考算法（Version Selection Reference）

- 文档类型：设计提案（**探索性草案，非规范性**）
- 状态：探索性草案
- 日期：2026-08-21
- 相关理论：Russ Cox, *Minimal Version Selection*（research.swtch.com/vgo-mvs）

## Summary

本提案从 Go 生态的 Minimal Version Selection（MVS）蒸馏一组可复用的**版本选择参考算法**，供需要"简单版本选择"的协议 definition 声明采纳。

本提案**不规定** core 或其他任何协议必须采用任何选择模型。Core 不默认统一选择规则（见 core.zh.md Rationale：统一选择规则属于协议 definition）；实现可以完全不采用本提案的任何内容，自主实现自己的协商与选择逻辑。本提案只是把一组经过理论验证的性质整理成可复用部件，供需要的协议按需采纳。

## Motivation

Core 只负责调度协议 definition，把"如何选择版本"留给各协议决定。实际中，多个参与方对同一协议族提出不同最小版本要求时，协议作者需要一组**可预测、可复算、实现简单**的选择语义。MVS 提供了这样的候选：它只用"最低版本需求"一种约束，答案唯一且可线性时间计算。

与此同时，DSH 的协商是**运行时参与者语义**，不是 Go 模块的构建期依赖解析。本提案明确两者的边界，只蒸馏与运行时协商同构的性质，并标注哪些 MVS 性质在 DSH 假设下不成立。

## Guide-level explanation

一份协议 definition 可以在其规范中声明"采纳版本选择参考算法"。采纳后，该协议族的协商语义按以下规则执行：

1. **最低版本需求**：参与方对某协议族的 requirement 只表达一个**最低**版本（"我至少需要 v"），不表达上限或互斥。
2. **选择 = 满足所有要求的最旧版本**：若多个参与方提出不同最低版本要求，选择其中**最高的最低版本**（max of minimums）。单一候选时退化为该版本本身，选择无行为变化。
3. **无隐式升级**：协商与组合**不主动升级**到任何参与方未要求的版本。升级必须由参与方显式提出。
4. **结果可复算**：同一组规范化声明、同一组 protocol definitions 和同一份显式 policy 输入，必须产生等价的协商结果（与 core Determinism 节一致）。

### 唯一最小答案的适用条件

MVS 证明"唯一最小答案"依赖两个前提：版本之间存在**全序**，且兼容关系是**单调的**（新版本是旧版本的超集，即区间语义）。在 DSH 中，`apiVersion` 是字符串，core 明确不假定同一 major 下的 alpha、beta 和 stable 必然互通，兼容关系由 definition 声明——因此：

- **当 definition 声明了版本全序 + 单调兼容**时，本算法给出唯一最小答案，结果可被其他实现独立复算；
- **当兼容关系是任意 pairwise 声明**（无全序、无单调性）时，唯一最小性**不保证**。采纳本算法的 definition 必须如实声明其兼容关系属于哪种情形。

### 排除与替换（可选的未来扩展）

MVS 允许模块声明局部排除/替换，前提是它们必须是**无条件的**（在协商开始前决定，内容不依赖选择结果）且**局部的**（只被声明方自己的协商范围咨询）。这两个性质是算法保持简单（不落入 NP 完全搜索）的原因。

Core 目前没有排除/替换概念。本提案仅记录该扩展方向作为未来参考，采纳协议的 definition 若引入排除/替换，必须保持"无条件 + 局部"，不得引入条件排除（会导致 NP 完全的选择问题）。

### 与 MVS 的假设差异

| MVS 假设 | DSH 对应 |
| --- | --- |
| 模块遵循 import compatibility（SemVer 向后兼容），要求只给最低版本 | 兼容性由协议 definition 声明；requirement 只给最低版本（由采纳本算法的 definition 规定） |
| 版本全序（新/旧可比较） | 由 definition 声明，core 不预设 |
| 构建期一次性解析 | 运行时协商（composition preflight + core 协商 + lifecycle staged/live）；选择发生在协商时点 |
| "顶层模块"控制排除/替换 | core 无"顶层模块"角色；"无条件 + 局部"是保留性质，不映射到任何特权角色 |

## Reference-level explanation

### 算法 1：构造候选集（max of minimums）

输入：一组参与方对某协议族的 requirement（每个是一个最低版本）。

输出：被选择版本。

过程：取所有 requirement 中的最高最低版本。若没有 requirement，则该协议族不参与选择。

### 算法 2：单一升级（显式要求时）

参与方显式要求某协议族使用某个更高版本时，将该版本视为该参与方的新最低要求，重新执行算法 1。不得静默升级其他参与方未要求的版本。

### 算法 3：单一降级（显式要求时）

参与方显式要求某协议族使用某个更低版本时，逐项检查其他参与方的最低要求：若某要求与该降级不兼容（其最低版本高于降级目标），记录为需协商的 issue；**降级操作不得隐式升级其他版本**（若需要先升级再降级，必须由参与方显式提出）。

### 算法 R：最小 requirement 列表（可选项）

需要把选择结果写回某参与方的声明时，可访问 MVS 的 reverse postorder 算法求得最小 requirement 集合。本提案不强制要求该步骤；它只在需要"把协商结果固化为参与方声明"时作为参考。

### 循环依赖

MVS 明确要求算法处理循环依赖（模块互相依赖）。采纳本算法的 definition 应声明其对循环依赖的处理：要么指定确定性破环规则，要么明确排除循环场景；**不得在循环输入下产生不确定结果**。与 lifecycle 的环处理（composition rule / atomic activation）的关系由相应协议定义。

### 与 composition 的关系

本算法只有"最低版本"一种关系语义，不定义 depends/recommends/breaks/conflicts。采纳本算法的 definition 若需要更丰富的关系语义，必须与 `@dsh-std/composition` 的关系模型（composition.zh.md）显式衔接，说明两种语义如何共存。安装与版本决策仍以 component 为单位。

## 与 core 的边界（非目标）

- 本提案**不是** core 的规范扩展；core 不因本提案获得任何新的 MUST 语义；
- Core 不解释 requirement 的 spec（core.zh.md："Core 保留该数据，但不解释其字段"）；本算法由采纳它的 definition 解释；
- 本提案不改变任何已有坐标、schema、状态机或协商流程；
- 本提案定位为 definition 层可复用参考实现，可被未来更合适的模型取代。

## Drawbacks

- 唯一最小答案在非单调兼容关系下不成立——采纳的 definition 必须如实声明适用条件；
- "最低版本"模型较简单，无法表达互斥、偏好或环境策略；需要这些能力的协议应定义自己的协商输入（core.zh.md："协议若需要优先级、用户选择或环境策略，必须在自己的协商输入中明确表达"）；
- 版本全序的来源（谁定义新/旧）需要采纳的 definition 额外声明，MVS 的 SemVer 推定不能照搬。

## Alternatives

- **不做任何规定**：维持现状，各协议自行定义选择语义。本提案的存在不改变这一选项；它只是给需要的协议多一个可复用部件。
- **core 统一选择**：已被 core.zh.md Rationale 否决（core 没有足够信息给出统一选择规则）。
- **区间/范围协商**：参与方声明支持范围而非最低版本。这是另一种模型，可独立提案，与本提案不冲突。

## Unresolved questions

- "版本全序"由 definition 声明时，是否需要标准化的声明格式（schema）？
- 排除/替换扩展是否值得进入任何具体协议的 definition，还是保持纯参考？
- 与 composition 关系语义的完整衔接方案。
